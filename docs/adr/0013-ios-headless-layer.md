# ADR 0013: An iOS layer over the same core, headless first

**Status:** accepted · 2026-10 · builds on [ADR 0001](0001-cpp-core.md) and [ADR 0006](0006-sans-io-session.md)

The code is on the [`ios` branch](https://github.com/AlekseyAzarov/tarkov-companion/tree/ios/), not in `main`.

## Context

The core was written so that a second platform would be cheap: everything
that knows about tarkov.dev, caching and fallbacks is in the C++ session, and
a platform layer only executes its actions. Until now only Android existed,
so that claim had not been tested.

The SDK is developed on Windows. Swift can't be built here; the only Mac
available is a GitHub Actions macOS runner, so every change to the iOS layer
is checked in CI only.

## Decision

### The core as a static XCFramework

[`scripts/build-ios-core.sh`](https://github.com/AlekseyAzarov/tarkov-companion/blob/ios/scripts/build-ios-core.sh) builds the
unchanged core with CMake for iOS devices (arm64), the iOS simulator (arm64,
x86_64) and macOS (for tests on the host), and packs the three static
libraries with the C header and a module map. The only change to the core was
giving iOS the same size flags as Android (`-Os`, no exceptions, no RTTI).

Swift calls the C API directly through the module map. There is no glue
layer like the JNI bridge: Swift passes strings and `Data` as pointer and
length, which the C API takes anyway.

### A Swift package that executes the session's actions

[`sdk-ios`](https://github.com/AlekseyAzarov/tarkov-companion/tree/ios/sdk-ios) mirrors the Android executor:

- `SessionDriver` runs the core and its actions on one serial dispatch queue;
  only HTTP leaves it, through the host's `HttpTransport`, and its completion
  comes back to the queue. Every action that expects an answer gets one, even
  when it can't be read.
- The default transport is `URLSession` with an ephemeral configuration: no
  HTTP cache, no redirects, 8 MB at most, as on Android.
- `DiskStore` keeps the cache under Caches and the player's data under
  Application Support, with hashed file names and atomic writes.
- Constants come from the same `contracts/` files, generated by
  [`scripts/generate-swift-contract.mjs`](https://github.com/AlekseyAzarov/tarkov-companion/blob/ios/scripts/generate-swift-contract.mjs).

### A Swift-shaped public API

`searchItems` and `recommendation(forItemId:)` are `async throws`.
Cancelling the calling task cancels the request in the core and throws
`CancellationError`; nothing is delivered after that. Errors are
`CompanionError`, whose `Code` is a struct of named values rather than an
enum, so new codes are not a breaking change. `PlayerProfile` validates in a
throwing initializer instead of a builder. Nothing in the API crashes the
game on bad input.

### Headless first

Left out for now, each needing work of its own on iOS:

- the overlay: a `WKWebView` carrying the bridge protocol, which on iOS has no
  `MessagePort` to hand to the page;
- sign-in: `ASWebAuthenticationSession` and the Keychain;
- favourites sync and the remote flags.

The core asks for these only when they are configured, so the iOS layer
leaves their settings out. A secret read, which only sign-in causes, is
answered "not found".

### Tested on the same data as Android

The tests use the recorded responses in `contracts/fixtures` and the golden
recommendation the core and the Android tests are pinned to, so the iOS
build of the core is checked against the same bytes. CI runs them on macOS
and on the iOS simulator, and builds for devices.

## Consequences

- The core moved to a second platform without a source change. The Swift
  layer is about 1,000 lines of executor and stores, against 2,600 lines of
  Kotlin that also cover the overlay, sign-in and favourites.
- The same rules (queries, cache policy, fallbacks to the cache and the
  catalog) run on both platforms by construction.
- The core linked for arm64 devices is 230 KB, against 322 KB for the
  Android library, which carries its own libc++
  ([footprint.md](../footprint.md#on-ios)).
- Async Swift can't be called from Objective-C or C++. A game calling from
  Unreal or Objective-C++ would need a completion-handler variant or a thin
  C entry point.
- Without exceptions in the core, running out of memory aborts the process,
  as on Android.
- No local Mac: a mistake in Swift is found a CI run later. Compiler errors
  and failed tests appear as annotations on the run.
